# 常用概念

- **地图文档**: `docs/ui-protocol/map.md `
- **元素布局说明文档**: 有地图文档指向的 `docs/ui-protocol/layouts/` 路径下的对应元素布局说明文档

# UI 语义路径定位 Skill

## 目标

当用户通过“元素结构路径”来描述一个页面中的修改目标时，你需要把这条路径作为 **UI 语义定位指令** 来处理，而不是把它当成普通文本搜索。

本 skill 的目标是：

1. 识别用户提供的语义路径
2. 优先读取地图文档
3. 根据元素布局说明文档理解该节点的业务语义、英文 id、类型、父子层级和推荐路径
4. 基于这些信息，定向定位可能的前端实现文件
5. 尽量缩小检索范围，避免在整个项目做无差别搜索
6. 在找到文件后，继续定位最可能的相关代码段
7. 支持后续执行修改，而不是停留在理解层

---

## 触发条件

当用户出现以下任一表达时，应触发本 skill：

- `元素结构：主窗口.程序准备容器.登录页.PMS账号输入框`
- `修改 主窗口.程序准备容器.登录页.PMS账号输入框`
- `把 主窗口.程序准备容器.Step 03.操作按钮.开始监听按钮 改成绿色`
- `调整 登录页.PMS账号输入框 的宽度`
- `修改 root.prep_container.login_page.account_input`
- `定位 主窗口.程序拷贝容器.运行日志.日志列表`

只要用户使用了：

- 中文语义路径
- 英文协议路径
- 中英混合路径

都应视为 UI 语义路径定位请求。

## 核心原则

### 原则 1：先理解协议，再找代码
必须优先读取：地图文档.元素布局说明文档

不要在尚未读取 design 文档前，直接全局搜索整个项目。

### 原则 2：路径是语义定位，不是字符串检索

用户输入的：

```text
主窗口.程序准备容器.登录页.PMS账号输入框
```

不是要求你全文搜索这串字，而是要求你理解其在 UI 协议中的节点含义。

### 原则 3：优先小范围定向定位

在理解到目标节点后，应优先定位最可能的代码区域，例如：

* 对应页面文件
* 对应模块文件
* 对应组件文件
* 对应步骤页文件
* 对应表单组件文件

避免上来就对全项目进行宽泛搜索。

### 原则 4：先文件级定位，再行级定位

正确顺序是：

1. 定位目标所属页面 / 模块 / 组件文件
2. 再定位具体 JSX / TSX / Vue template / 组件定义 / 表单项
3. 再执行修改

### 原则 5：保留语义链路

在定位时，始终保留以下映射链：

```text
用户路径
→ map.md 节点
→ 推荐英文 id
→ 所属模块
→ 候选组件文件
→ 具体代码位置
```

## 标准执行流程

当用户使用语义路径描述修改目标时，严格按以下顺序执行：

---

### 第一步：读取

先打开并阅读：地图文档.元素布局说明文档

重点提取以下信息：

* 页面结构树
* 节点中文名称
* 节点英文 id
* 节点类型 type
* 父级路径
* 推荐语义路径
* 示例路径
* 命名规则

如果 design 文档不存在：

1. 明确告知当前缺少 UI 控制协议文档
2. 优先建议先执行“创建UI控制协议”
3. 若用户当前任务必须继续，再基于现有路径做谨慎推断定位

---

### 第二步：解析用户提供的路径

将用户输入路径拆解为节点链，例如：

```text
主窗口.程序准备容器.登录页.PMS账号输入框
```

拆为：

* 主窗口
* 程序准备容器
* 登录页
* PMS账号输入框

然后到 design 文档中寻找对应映射：

* 完全匹配中文 name
* 匹配推荐英文 id
* 匹配中英混合路径
* 匹配父子层级关系

必须优先做**层级语义匹配**，不是只按单个词碰撞搜索。

---

### 第三步：推断目标节点属性

从 design 文档中获取该节点的上下文，包括：

* 当前节点的英文 id
* 当前节点 type
* 所属页面 / 区域 / 容器
* 所属 step
* 相邻节点
* 所在模块名称

例如：

```text
主窗口.程序准备容器.登录页.PMS账号输入框
```

可能映射为：

```text
root.prep_container.login_page.account_input
```

并可推断：

* 所属页面：登录页
* 所属容器：程序准备容器
* 所属模块：登录表单
* 节点类型：input

---

### 第四步：按模块缩小搜索范围

在理解语义后，优先缩小搜索范围，而不是全局搜索。

缩小范围时遵循：

#### 1. 先找页面级文件

例如：

* `LoginPage.tsx`
* `login-page.vue`
* `PrepContainer.tsx`
* `Step01.tsx`
* `Step03.tsx`

#### 2. 再找模块级文件

例如：

* `LoginForm.tsx`
* `ProjectSearchBar.tsx`
* `ProgramList.tsx`
* `RuntimeLogPanel.tsx`

#### 3. 再找控件实现

例如：

* `AccountInput`
* `FormItem`
* `Input`
* `TextField`

#### 4. 最后才做局部关键词补充搜索

搜索应优先围绕以下关键词组合：

* 节点英文 id
* 中文业务名的英文语义
* 所属模块名
* 相邻按钮名
* step 名称
* type 名称

例如对于 `PMS账号输入框`，优先搜索：

* `account_input`
* `login`
* `pms`
* `account`
* `username`
* `form`
* `登录`

但必须以 design 文档中的结构推断为主。

---

### 第五步：定位到具体代码段

进入候选文件后，继续定位最相关片段，例如：

* 表单定义
* label / placeholder
* input 组件
* 绑定字段名
* 事件函数
* 样式 className
* 组件 props

如果发现是复合组件：

* 先记录外层容器位置
* 再递进到子组件文件
* 保持路径与组件关系一致

---

### 第六步：执行修改时的要求

完成定位后再做修改。修改时要遵循：

* 尽量最小范围修改
* 不要顺手重构无关代码
* 不要因为找不到立即扩大到全项目全面搜索
* 若存在多个候选位置，优先选择与 design 语义最一致的那个
* 若确有歧义，应在结果中明确说明候选关系

---

## 搜索策略

### 优先级顺序

必须遵循以下搜索优先级：

```text
1. docs/ui-protocol/map.md
2. 对应页面文件
3. 对应模块文件
4. 对应组件文件
5. 局部关键词搜索
6. 必要时才扩大范围
```

### 不推荐行为

禁止一开始就做以下行为：

* 全项目搜“输入框”
* 全项目搜“标题”
* 全项目搜“button”
* 全项目搜“主窗口”
* 无结构地搜整个仓库所有 tsx/vue/js 文件

这些做法命中面太大，会降低效率与准确性。

## 路径识别规则

### 1. 中文路径

例如：

```text
主窗口.程序准备容器.登录页.PMS账号输入框
```

### 2. 英文路径

例如：

```text
root.prep_container.login_page.account_input
```

### 3. 中英混合路径

例如：

```text
prep_container.登录页.account_input
```

### 4. 省略上层路径的相对路径

例如：

```text
登录页.PMS账号输入框
Step 03.开始监听按钮
运行日志.日志列表
```

若 design 文档中能唯一定位，可直接使用。

---

## 节点理解规则

对于常见节点，要自动理解其修改倾向：

### input

通常对应：

* placeholder
* label
* value 绑定
* 宽度
* 样式
* 校验逻辑

### button

通常对应：

* 文案
* 颜色
* disabled 状态
* 点击行为
* 图标
* 样式

### list

通常对应：

* 列表项结构
* 行渲染
* 排序
* 空态
* 滚动
* 样式

### state

通常对应：

* 状态标签
* 状态文案
* 颜色
* 图标
* 状态切换逻辑

### log

通常对应：

* 日志行渲染
* 时间格式
* 描述结构
* 滚动区域
* 日志级别颜色

## 输出与行为要求

当接收到用户的路径修改请求时，你的实际行为应尽可能体现以下顺序：

1. 先阅读 `地图文档.元素布局说明文档`
2. 说明你已按 design 协议理解目标节点
3. 定向定位前端相关文件
4. 找到最可能的代码位置
5. 在该位置附近执行修改

在回应中，应优先使用类似表述：

* 已根据 `地图文档.元素布局说明文档` 将该路径映射到目标节点
* 当前节点位于登录页 / Step 03 / 运行日志模块
* 我将优先检查对应页面和子组件，而不是做全局搜索
* 已定位到相关实现文件与代码段

不要表现得像在进行无序盲搜。

---

## 缺失 map.md 时的回退策略

如果 `地图文档.元素布局说明文档` 不存在：

### 第一优先

建议先创建 UI 控制协议：

```text
创建UI控制协议
```

### 第二优先

若用户明确要求立即改动，则可以使用以下回退流程：

1. 根据用户路径做人工语义推断
2. 优先找页面入口组件
3. 再找局部模块组件
4. 最后才做小范围关键词搜索

但必须明确说明：当前缺少 design 协议，定位精度会下降。

## 修改任务中的默认行为

当用户在描述路径后同时提出修改意图，例如：

* `把 主窗口.程序准备容器.登录页.PMS账号输入框 宽度改大一点`

* `调整 运行日志.日志列表 的行高`

你应自动理解为：

1. 路径定位任务
2. 前端修改任务

不要只解释路径，不执行修改。

## 示例

### 示例 1

用户说：

```text
修改 主窗口.程序准备容器.登录页.PMS账号输入框 的 placeholder
```

你的处理方式：

1. 读取 `地图文档.元素布局说明文档`
2. 将其映射为类似 `root.prep_container.login_page.account_input`
3. 推断目标位于登录表单模块
4. 优先定位 `LoginPage` / `LoginForm` / 登录表单相关组件
5. 找到 input 代码段后修改 placeholder

---

### 示例 2

用户说：

```text
把 Step 03.操作按钮.开始监听按钮 改成绿色
```

你的处理方式：

1. 从 design 中确认 `step_03.action_group.start_monitor_button`
2. 判断目标位于 Step 03 的操作区
3. 优先定位 Step03 页面和按钮区域组件
4. 修改按钮样式相关代码

---

### 示例 3

用户说：

```text
调整 程序拷贝容器.运行日志.日志列表 的间距
```

你的处理方式：

1. 从 design 中映射到运行日志区域
2. 优先找 `RuntimeLog` / `LogList` / `CopyContainer` 相关文件
3. 定位日志列表渲染处和样式定义处
4. 局部调整样式

## 与 UI 控制协议 Skill 的关系

本 skill 依赖：

```text
地图文档.元素布局说明文档
```

该文件通常由以下 skill 生成：

* UI 控制协议生成 Skill
* 即通过“创建UI控制协议”生成的 design 文档

因此本 skill 是 **第二阶段技能**：

* 第一阶段：创建协议
* 第二阶段：利用协议精准定位与修改

---

## 禁止事项

* 不要忽略 `地图文档.元素布局说明文档`
* 不要把语义路径当成普通字符串暴力搜索
* 不要在没有理解节点语义时直接全项目搜索
* 不要因为搜索方便就跨整个仓库盲找常见词
* 不要只解释位置，不继续执行用户要求的修改
* 不要脱离 design 文档自行发明不一致的节点命名
* 不要在无关文件中做顺手重构

---

## 成功标准

当本 skill 正常工作时，应达到以下效果：

* 用户可直接用语义路径描述修改位置
* Codex 能优先读取 `地图文档.元素布局说明文档`
* Codex 能快速理解目标节点位置
* Codex 能优先定位到相关页面/模块文件
* Codex 避免全项目大范围搜索
* Codex 能更快落到可修改的具体代码段
