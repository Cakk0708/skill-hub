# 部署要求

## 镜像构建与发布

生产发布按以下边界进行：

```text
源码与 Dockerfile → 构建镜像 → 推送镜像仓库 → 线上拉取固定版本 → Compose 启动
```

- 生产镜像使用不可变版本标签或 digest；禁止用 `latest` 作为生产版本标识。
- 生产 Compose 使用 `image:`，不使用 `build:`。构建在受控构建环境完成，镜像仓库是生产主机取得应用镜像的来源。
- 镜像架构、运行时配置和必要模型/静态资产应与目标主机匹配。发布清单记录每个服务实际使用的镜像引用。
- 服务按独立发布或扩缩容边界拆分镜像和容器；共享生命周期的组件可以同批发布，不机械要求每个源码目录都成为一个服务。

## 生产 Compose 与配置

- Compose 负责容器编排、服务依赖、网络、端口、数据挂载和运行环境，不在主机上构建应用源码。
- 如果项目采用共用 Compose 加环境 overlay，生产命令始终使用同一组文件、env file 和 project name。切换工作目录或漏掉某个 Compose 文件可能创建不同的服务、网络或 volume。
- 生产秘密从受保护的环境文件或秘密管理系统注入；不写入镜像、源码、Compose 明文默认值或构建参数。渲染配置时避免把含秘密的完整输出写入日志或聊天记录。
- 主机端口只向实际需要访问的网络开放；数据库等内部服务默认仅在 Compose 网络内可访问，除非架构明确要求外部访问。

## 状态与备份

- 数据库、上传文件、业务状态和运行所需模型必须落在持久化 volume 或明确的宿主机目录中，不能只留在容器可写层。
- 部署前确认数据卷和 bind mount 指向预期位置。备份数据库和关键文件，并确认恢复方式；涉及数据库 schema 迁移时，使用与应用发布匹配的迁移步骤，不假设迁移总能自动反向执行。
- 不用 `docker compose down -v` 或全局 volume 清理命令作为普通升级步骤。删除 volume、清理数据目录或改变卷名之前，先确认数据所有权、备份和迁移路径。

## 升级、验收与回滚

1. 核对目标 Compose 项目、当前镜像、服务名、网络、端口和数据挂载；确认发布版本与目标主机架构兼容。
2. 发布前检查 Compose 能否解析，并核对服务列表与镜像列表。检查输出时避免展示已展开的秘密。
3. 拉取目标镜像，按发布步骤执行迁移和启动。只更新单个服务时，确保其依赖和 Compose 配置与线上当前项目一致。
4. 检查容器健康状态、启动日志和应用级探测；只有目标服务可用且关键数据读写符合预期，才记录发布完成。
5. 保留上一版镜像、对应 Compose 配置和必要备份。出现故障时依据应用与 schema 兼容性回滚；数据库迁移需要独立评估，不能仅通过切回旧镜像来推断数据已恢复。

任何部署操作都应针对已确认的线上 Compose 项目执行。不要仅凭示例路径、容器名或旧发布记录推断当前生产状态。
