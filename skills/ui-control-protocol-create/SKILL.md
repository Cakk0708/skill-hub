# 常用概念

- **地图文档**: `docs/ui-protocol/map.md`
- **元素布局说明文档**: 有地图文档指向的 `docs/ui-protocol/layouts/` 路径下的对应元素布局说明文档

# UI 控制协议生成 Skill
## 任务目标

当用户说“创建UI控制协议”时，你的任务不是编写一篇介绍性文档，而是：

1. 读取用户提供的页面结构、布局树、元素树
2. 将其整理为一份 **UI 语义结构映射文档**
3. 供后续 Codex 根据“主窗口.程序准备容器.登录页.PMS账号输入框”这类路径快速理解目标位置
4. 将结果覆盖写入元素布局说明文档

---

## 文档用途

生成的元素布局说明文档只服务于以下目的：

* 让 Codex 理解页面的语义路径
* 让 Codex 根据路径快速定位前端实现位置
* 让用户后续可以直接用路径描述改动目标
* 作为页面元素结构与前端实现之间的中间映射层

不要把文档写成概念介绍、教程、说明书、评审文档。

---

## 输出要求

最终输出必须是 **高度结构化、强约束、偏检索用途** 的 Markdown 文档。

### 必须包含的内容只有以下 4 部分：

```md
# UI 结构映射

## 1. 页面结构树
## 2. 关键节点映射表
## 3. 路径使用规则
## 4. 定位约束
```

除这 4 部分外，不要额外扩展“适用范围”“协议背景”“设计目标”“长篇示例解释”“概念分析”“为什么这样设计”等章节。

---

## 强制输出规则

### 规则 1：禁止写泛化说明

不要输出以下类型内容：

* 本协议用于……
* 协议目标是……
* 适用范围……
* 自动化脚本描述……
* 人工指令到页面元素的映射……
* 页面重构后应尽量兼容……
* 任何与当前页面直接映射无关的泛化解释

这些内容全部不要写。

### 规则 2：禁止长段落解释

整份 design.md 应以：

* 树结构
* 表格
* 清单
* 路径列表

为主，不要写大量自然语言段落。

### 规则 3：禁止举大量“含义解释型示例”

不要写：

* 示例 1 含义是……
* 示例 2 含义是……

只保留必要的路径规则即可。

### 规则 4：禁止脱离当前页面泛化

所有内容必须紧贴用户当前提供的页面结构，不能写成通用 UI DSL 教程。

### 规则 5：禁止替用户扩写主题

不要主动补充用户没有给出的“长期维护建议”“团队协作建议”“自动化测试建议”“文档治理建议”。

---

## 生成内容要求

---

### 第一部分：页面结构树

将用户给定的结构整理为清晰树状结构。

要求：

* 保留原始中文语义名称
* 保持层级清晰
* 不擅自增加无关节点
* 对明显重复节点可在名称前补充父级语义以避免歧义，但不要过度改名

示例风格：

```md
## 1. 页面结构树

- 主窗口
  - 导航栏
    - 标题
      - 子标题
      - 主标题
    - 监听状态
      - 未监听
      - 监听中
      - 停止监听（按钮）
  - 程序准备容器
    - 登录页
      - 标题
      - PMS 账号（输入框）
      - PMS 密码（输入框）
      - 登录验证（按钮）
      - 提示信息
```

不要在这一节里穿插说明性文字。

---

### 第二部分：关键节点映射表

这是文档最核心部分。
必须为主要节点生成规范化映射表。

每条映射至少包含以下字段：

* 中文名称
* 英文 ID
* 类型
* 父路径
* 推荐路径

推荐使用 Markdown 表格。

字段要求：

| 字段    | 含义                                                             |
| ----- | -------------------------------------------------------------- |
| 中文名称  | 用户使用的语义名                                                       |
| 英文 ID | 稳定英文标识，snake_case                                              |
| 类型    | 如 window / container / section / input / button / list / state |
| 父路径   | 父节点推荐路径                                                        |
| 推荐路径  | 当前节点完整推荐路径                                                     |

示例风格：

```md
## 2. 关键节点映射表

| 中文名称 | 英文 ID | 类型 | 父路径 | 推荐路径 |
|---|---|---|---|---|
| 主窗口 | root | window | - | root |
| 程序准备容器 | prep_container | container | root | root.prep_container |
| 登录页 | login_page | section | root.prep_container | root.prep_container.login_page |
| PMS 账号（输入框） | account_input | input | root.prep_container.login_page | root.prep_container.login_page.account_input |
| 登录验证（按钮） | login_submit_button | button | root.prep_container.login_page | root.prep_container.login_page.login_submit_button |
```

要求：

* 以“关键节点”为主，不要求把所有纯文本节点都做成表格
* 但必须覆盖所有可交互节点、列表节点、状态节点、核心展示区节点
* Step 节点必须标准化为 `step_01`、`step_02`、`step_03`

---

### 第三部分：路径使用规则

这一节只写最小必要规则，禁止展开成教程。

必须只包含以下内容：

1. 使用 `.` 表示层级
2. 路径优先使用英文 ID
3. 中文路径可作为自然语言别名
4. 同名节点必须带父路径
5. 列表项路径允许使用 `[字段=值]` 形式补充限定

推荐格式：

```md
## 3. 路径使用规则

- 使用 `.` 表示父子层级
- 优先使用英文 ID 路径，如 `root.prep_container.login_page.account_input`
- 中文路径可作为自然语言别名，如 `主窗口.程序准备容器.登录页.PMS 账号（输入框）`
- 同名节点必须补充父路径，避免歧义
- 列表项可使用限定表达式：
  - `project_list[item_name="xxx"]`
  - `program_list[program_name="xxx"]`
```

不要写额外解释。

---

### 第四部分：定位约束

这一节也必须非常短，只写给 Codex 用的定位约束。

必须包含：

* 后续收到语义路径时，优先按地图文档解析
* 优先按父级模块缩小范围定位前端文件
* 不要直接全项目搜索常见词
* 若 design 中存在推荐路径，优先按推荐路径映射
* 若存在多个同名节点，必须结合父路径判断

推荐格式：

```md
## 4. 定位约束

- 后续根据语义路径定位页面元素时，优先读取本文件
- 优先使用推荐路径映射到页面模块和组件范围
- 优先按父级容器、步骤页、功能区缩小代码搜索范围
- 不直接对全项目执行“标题”“按钮”“输入框”等宽泛关键词搜索
- 同名节点必须结合父路径解析
```

不要写成长篇分析。

---

## 命名规则

生成英文 ID 时遵循以下约束：

* 使用 snake_case
* 名称必须体现业务语义
* button 节点以 `_button` 结尾
* input 节点以 `_input` 结尾
* list 节点以 `_list` 结尾
* state 节点以 `_state` 结尾
* Step 节点统一为 `step_01`、`step_02`、`step_03`
* 登录页统一使用 `login_page`
* 主窗口固定为 `root`

不要在文档中单独展开成大段“命名规范说明”，只需在生成时遵守。

---

## 写入要求

生成后必须执行以下结果：

1. 确保目录存在：

```bash
mkdir -p .codex/docs
```

2. 将结果写入：

```text
docs/ui-protocol/layouts/{元素布局说明文档}
```

3. 若原文件存在，直接覆盖

---

## 执行流程

当用户说“创建UI控制协议”时，严格按以下顺序执行：

1. 读取用户当前提供的页面元素树 / 布局描述
2. 整理为页面结构树
3. 提取关键节点并生成映射表
4. 补充最小必要的路径规则
5. 补充最小必要的定位约束
6. 写入元素布局说明文档

---

## 输出长度控制

必须控制输出篇幅，避免产生冗长文档。

要求：

* 优先短结构，不写长说明
* 每一节都以“可检索、可映射、可定位”为目标
* 不要为了显得完整而补充无关章节
* 整份 design.md 应尽量保持紧凑

---

## 成功标准

当本 skill 执行完成后，`docs/ui-protocol/layouts/元素布局说明文档` 应满足：

* 用户能直接使用中文路径描述元素
* Codex 能根据元素布局说明文档理解这些路径
* Codex 能依据父级模块快速缩小前端定位范围
* 文档以结构映射为主，而不是解释性内容为主
* 没有大量偏离主题的概念性文字

## 输出风格硬约束

生成的 `docs/ui-protocol/layouts/元素布局说明文档` 必须更像“索引文件 / 映射文件 / 定位文件”，
而不是“方案文档 / 设计说明 / 协议介绍”。

如果输出中出现以下倾向，应主动压缩或删除：

- 背景介绍过多
- 解释性文字过多
- 示例分析过多
- 与当前页面映射无关的通用协议描述
