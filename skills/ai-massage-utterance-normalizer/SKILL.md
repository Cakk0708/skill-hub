# 按摩领域归一词维护

## 目标

把已经确认的 FunASR 相近词收敛到现有的按摩规范词，让后续确定性路由和 `MassageAgent` 只面对一套稳定业务词。归一化是 ASR 输出后的文本处理，不等于修改声学模型，也不等于新增设备命令。

必须同时满足以下边界：

- 保留用户原始 ASR 文本；只有归一后的文本进入按摩路由、`ConversationService` 和 `MassageAgent`。
- 归一化只输出主板无关的自然语言规范词，禁止输出岭阳功能码、键值、UART 字节、校验和或其他主板协议细节。
- 归一词必须收敛到已有业务词，不能为了容纳误识别词而新增第二套手法、目标、模式或程序枚举。
- 归一规则必须可重复执行：再次处理已经归一的文本时不得继续改变语义。

## 适用范围判断

先判断这次需求是否只是“别名归一”：

1. 如果目标是现有规范词，例如 `楼捏 -> 揉捏`，使用本技能，通常只修改归一化规则、回归测试和词条文档。
2. 如果目标词代表新的业务能力、`DeviceCommand`、`massage.*` 动作或语义程序，不能只增加归一词。应继续完成 `DeviceCommand -> massage.* -> self.massage.* -> MassageCommand -> BoardAdapter` 的完整链路，并按需使用仓库中的 `laya-massage-intent` 技能。
3. 如果问题是模型声学混淆、热词配置或无法从文本可靠判断的口音问题，先记录原始 ASR 样本并单独评估 FunASR/模型方案；不要用宽泛的全局替换掩盖不确定性。

## 当前实现位置

本仓库的统一入口是：

`xiaozhi-esp32-server/main/xiaozhi-server/core/assistant/massage_domain/utterance_normalizer.py`

关键接口和约定：

- `normalize_massage_utterance(text)`：返回 `MassageUtteranceNormalization`。
- `raw_text`：原始输入，必须保留。
- `normalized_text`：归一结果，提供给按摩语义链路。
- `rule_ids`：稳定、可追踪的命中规则编号，按首次命中顺序记录并去重。
- `MASSAGE_UTTERANCE_NORMALIZATION_VERSION`：当前归一化契约版本，现为 `massage-utterance-v1`。
- 同一规范词的多个已确认 ASR 入口应集中在同一个别名集合或规则表项中，共用规范词和适用边界；不要为每个近音词复制一段分支代码。

适配器和 Agent 已经会把归一结果写入 `input_normalization` 及会话轮次记录，因此不要另建第二个归一化入口，也不要只在某个 LLM prompt 中添加同义词。

## 新增一条归一规则的工作流

### 1. 收集并确认原始样本

保留用户实际说法，不要先把句子概括成意图。每条样本至少记录：

- 原始 ASR 文本，包括标点、数字写法、口语助词和上下文。
- 期望规范文本。
- 触发所需的业务上下文，例如开关动作、力度动作、身体部位、手法或按摩方案。
- 不能触发的普通语境、问句、否定句和条件句。
- 如果是多轮表达，记录已有 `current_intent`、设备状态和期望结果。

只有在“误识别词 -> 规范词”的业务含义已经确认时才添加规则。单个字形相近但含义不确定时，先不归一。

### 2. 主动枚举相近词并筛选入口

新增一个领域归一词时，不能只处理用户当前给出的那个原词。以“原始 ASR 词 -> 已有规范词”为中心，主动回看同一目标下可能出现的近音入口，至少检查：

- 同音、近音以及声母、韵母、声调或方言差异造成的常见识别字；
- 单字替换、漏字、多字、重复字、词边界变化和常见 ASR 分词错误；
- 已有日志、用户原话、测试样本和同一目标的历史别名，避免漏掉已经存在的入口；
- 会不会与另一个按摩目标、手法、模式、程序或普通词混淆。

对候选词逐个分级：

- 有真实 ASR/日志样本，或已有稳定领域证据且业务含义相同：加入本次新增的别名集合，复用同一规范词；如果上下文边界不同，保留独立规则 ID 和各自最窄的上下文。
- 只有语言学上的可能性、没有样本或业务确认：记录为待确认候选，不直接进入生效归一表。
- 可能改变业务目标、参数或普通语句含义：拒绝加入，即使字面或读音相近。

例如补充 `气男 -> 气囊` 时，要主动检查 `去囊` 等同一目标的已确认入口，并整理为同一别名规则组；但不能因为都含有“气”就把普通的“气压”表达无条件全局替换。相近词扩展必须增加对应正例和普通语境负例，确保候选词确实收敛到同一业务词且不会误触发。

### 3. 选择最窄的实现方式

根据歧义程度选择规则位置：

- 明确只属于按摩手法的词，加入 `normalize_massage_utterance` 内的别名表，并为规则分配唯一 `rule_id`。
- 同一规范词的多个入口放入一个可查找的别名变量或规则表项；不要为相同的替换和上下文判断新增重复 `if` 分支。
- 可能出现在普通对话中的词，使用现有的上下文匹配辅助函数，并选择最小必要的 marker 集合；禁止直接全局 `replace`。
- 会与另一个别名级联、产生重复目标或改变参数含义的表达，先增加完整短语规则，再执行单词级规则。
- 开关目标类误识别词必须限制在明确的目标附近，不能把普通句子中的同音字改成 `关`、`开` 等控制词。

实现时应保持当前函数的行为：用紧凑文本判断上下文，用原始排版文本执行替换，从而保留标点、数字和口语助词；尊重问句、否定、禁止和条件上下文保护逻辑。

规则编号建议使用稳定的分组命名，例如：

```python
("ASR相近词", "已有规范词", "technique.xxx_to_knead")
```

不要把具体主板功能码、协议字段或临时日志编号放入 `rule_id`。

### 4. 维护版本和文档

- 仅新增向后兼容的别名、返回结构未变化时，保持 `massage-utterance-v1`，增加新的 `rule_id`。
- 修改已有映射、上下文边界或规范词含义时，先评估历史日志和会话重放影响；必要时升级版本并同步更新测试、文档和观测字段。
- 在 `docs/按摩语音词条及产品测试清单.md` 的归一化表中增加原词、上下文、归一词、`rule_id` 和期望业务结果。
- 仅新增归一词不需要修改 README 业务主链路时序图；只有链路职责或接口发生变化时才更新架构文档。

## 必须补充的测试

测试文件：

`xiaozhi-esp32-server/main/xiaozhi-server/tests/massage/test_utterance_normalizer.py`

采用表驱动样本，至少覆盖：

1. 正向按摩句：断言 `raw_text`、`normalized_text`、`rule_ids` 和版本。
2. 同一别名在普通语境中不被改写。
3. 问句、否定句、禁止句和条件句不产生设备控制意义。
4. 标点、数字、空格和口语助词的预期保留行为。
5. 归一化幂等性：对第一次的 `normalized_text` 再处理，结果不变且不新增规则命中。
6. 同一原句包含多个别名时，规则命中顺序稳定且不存在重复目标词。

如果归一后的规范词会触发设备能力，还要在 `tests/massage/` 增加接近真实入口的集成回归，确认：

- 进入正确的确定性按摩意图，不发生非预期通用 LLM 调用。
- `reply_text`、执行类型、语义动作和参数正确。
- 不出现“不支持”的错误兜底。
- 多轮补充语句不会重建或重启错误的完整按摩程序。
- 未生成任何岭阳功能码或 UART 原始字节。

## 验证命令

在 `xiaozhi-esp32-server/main/xiaozhi-server` 目录使用项目虚拟环境运行：

```bash
.venv/bin/python -m unittest tests.massage.test_utterance_normalizer -q
.venv/bin/python -m unittest discover -s tests/massage -q
git diff --check
```

如果规范词改变了确定性语义、能力声明、MCP 映射或执行编排，再补跑：

```bash
.venv/bin/python -m unittest discover -s tests/conversation -q
.venv/bin/python -m unittest tests.test_app_websocket -q
```

如果改动进入 ESP32 命令、Controller、BoardAdapter 或岭阳协议层，必须按仓库根目录 `AGENTS.md` 追加对应的 Mac 主机测试和 ESP-IDF 构建；单元测试不能宣称真实硬件联调成功。

## 交付说明

完成后报告：

- 每条原始表达、归一结果、触发上下文和 `rule_id`。
- 本次主动检查过的相近词候选，以及分别纳入别名集合、待确认或拒绝的依据。
- 首次命中的处理层，以及为什么不会误伤普通语境。
- 归一后的确定性回复、语义动作和关键参数；相对控制要说明状态基准。
- 实际运行的测试命令、数量和结果。
- 是否只改了服务端文本归一化，或是否进一步修改了语义动作和设备执行链路。

不要把“文本归一成功”描述成“ASR 模型已经听清”，也不要把“生成执行计划”描述成“按摩椅已经完成执行”；最终成功必须由 `accepted`、`sent`、`acknowledged`、`completed`、`failed` 或 `timeout` 等真实执行阶段决定。
