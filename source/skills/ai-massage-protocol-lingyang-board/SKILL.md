## 目标与边界

将一条原始报文解释为可核验的字段，并给出带证据等级的结论。只在 ESP32 岭阳适配层处理功能码、键值、字节偏移、ACK 和校验和；不要把这些细节泄漏到 MassageAgent、xiaozhi-server 或通用 UART 层。

阅读和修改时遵守仓库根目录 `AGENTS.md` 的唯一主链路。若用户只是询问报文，只读检查即可；若用户要求修复解析，将修改限制在 `xiaozhi-esp32/main/massage/lingyang/`，并补充主机黄金报文测试。

## 证据等级

按以下顺序建立结论，并在回答中明确标注：

1. **直接观测**：完整 UART TX/RX 原始字节、时间顺序、长度和校验和。
2. **当前协议表**：优先检查用户提供的《岭阳电子二代APP通信协议及说明V0.35_20230911.xls》。它是历史协议资料，不自动等于当前真板事实。
3. **当前代码与测试**：检查 `xiaozhi-esp32/main/massage/lingyang/` 和 `xiaozhi-esp32/tests/lingyang_protocol_test.cc`。
4. **历史代码或旧资料**：只能作为待验证参考，不得覆盖当前表格、当前适配器或真实回包。
5. **推断**：使用“可能”“如果该主板复用此布局”等措辞；没有证据时保留 `unknown` 和原始编号。

## 逐帧解析流程

### 1. 保留原始上下文

保留用户给出的完整十六进制字符串、日志时间、`RX/TX` 方向和前后相邻帧。去掉日志前缀和 hexdump 地址再解析：例如 `0x3fcea450` 是内存地址，不是协议字节。

将大小写、逗号和连续空格规范化，但不要删除或重排字节。若只有 RX 没有前一条 TX，先说明无法确认它对应哪一条请求。

### 2. 按 0 起始索引列出字段

普通帧使用以下布局：

```text
Byte 0      0x5A       帧头
Byte 1      0xA5       帧头
Byte 2      length     总帧长，包含校验和
Byte 3      function   功能码
Byte 4      value      键值或查询标志
Byte 5..N-2 data       数据区/扩展字段
Byte N-1    checksum   校验和
```

`0x14` 表示总长度 20；先检查实际字节数量等于 Byte 2，再读取功能码和值。帧过短、长度不一致或校验错误时，不继续猜测业务含义。

长度策略必须按功能码区分，不能把所有入站帧都强制当成 `0x14`：

- `LingyangFrameDecoder` 当前接受总长度 `0x06～0x80`，且要求 Byte 2 等于实际帧字节数并通过校验和。
- 当前普通命令 TX、普通功能码回复以及 `0x4D/0xFE` 查询回帧由适配器编码为 20 字节 `0x14` 普通帧。
- 当前真板兼容路径允许入站 `0x4D` 声控状态使用从 `0x06` 起的可变总长，例如 `0x06`、`0x08`、`0x10`、`0x12`、`0x14`；只读取 Byte 4 的声控值，不能因长度小于 20 而丢弃，也不能猜测额外字节的业务含义。
- 其他功能码仍须遵守当前状态解码器的 20 字节门槛，除非有新的直接观测和适配层测试证明其帧型。

### 3. 校验和

使用协议当前约定：

```text
checksum = sum(frame[0 .. length-2]) & 0xFF
```

校验和正确只证明字节帧完整，不能证明主板执行成功、命令被接受或目标状态已经完成。

### 4. 查协议表的准确位置

在该 XLS 中优先核对：

- 「APP功能码键值表」`C1`：列名是“功能码（十进制数值）”；`A17:D17` 是 `16 | 时间指令 | 16 | 0=无效；x表示定时x分钟`。因此线上 `0x10` 是十进制功能码 16 的十六进制表示。
- 「APP向设备发送数据格式」`F25`：Byte 3 是功能码；`G25`：Byte 4 是键值；`F26` 指向功能码键值表。
- 「主板向APP发送数据格式」第 4～7 行：主板通常在收到请求后回复，功能码应相同；`0xFE` 是查询状态标志；未标 `0x` 的数字按十进制，标有 `0x` 的按十六进制。
- 「主板向APP发送数据格式」第 16 行：仅明确规定功能码 63（线上 `0x3F`）加 `0xFE` 综合状态查询中，Byte 5 是剩余分钟、Byte 6 是剩余秒。

不要把表中十进制的 `16` 误读成线上字节 `0x16`；也不要把表中未定义的字段按邻近功能码套用。

## 当前已确认的关键语义

### 时间功能码 `0x10`

```text
5A A5 14 10 07 00 00 00 00 00 00 00 00 00 00 00 00 00 00 2A
```

在当前协议解释下：

- Byte 3 `0x10`：协议表十进制功能码 16，“时间指令”。
- Byte 4 `0x07`：键值 7，设置定时 7 分钟。
- Byte 19 `0x2A`：校验和正确。

### 查询标志 `0xFE`

`0xFE` 是查询状态标志，不是通用失败码：

```text
10 07   = 时间功能设置为 7
10 FE   = 查询时间功能当前状态
3F FE   = 查询综合状态
```

因此收到 `0x10 0xFE` 时，先称为“时间功能查询/状态回包”，不要直接称为“设置成功”或“设置失败”。

### 声控功能码 `0x4D` 的最终交互方案

历史 V0.35 表格的「APP功能码键值表」只明示功能码 77（线上 `0x4D`）的 `0=关闭、1=打开、0xFE=查询状态`，并在主板回复通用说明中明示回复字节数至少 20；当前项目在此基础上增加了 `2=临时连续对话`，并兼容真板主动上报的可变长度状态帧。回答时必须标注证据来源，不要把扩展语义伪装成历史表格明示。

当前代码和对话链路约定如下：

- 语义 `off`、`single`、`continuous` 由服务端下发给 ESP32；服务端和 MassageAgent 不携带 `0x4D` 或裸 UART 字节。
- ESP32 `MassageController` 将三种语义状态排队同步到岭阳适配层，TX 使用 20 字节普通帧 `4D00`、`4D01`、`4D02`。固件启动基线为 `1`，启动时发送 `4D01`；临时连续会话退出后恢复并发送 `4D01`。
- 主板发送 `4D/FE` 时，这是查询 ESP32 当前声控值的请求，不是状态值；`LingyangBoardAdapter` 在适配层生成当前值的 20 字节 TX 回帧，不能交给通用 UART、服务端或 LLM 处理。
- 主板主动上报 `4D00/4D01/4D02` 时，帧可以是已校验的 `0x06～0x80` 可变长度；`0x4D01` 的直接观测黄金帧为 `5A A5 06 4D 01 53`。适配层只使用 Byte 4 更新 `MassageState`，把未知值保留为 `unknown + raw_voice_control_code`。
- `4D/FE` 不更新 `MassageState.voice_control_mode`；`4D/00`、`4D/01`、`4D/02` 才是状态值。合法校验和只表示帧完整，不代表主板已经执行了设置。
- `off` 生效后 ESP32 会关闭唤醒词检测和监听，因此不能再依靠唤醒词自身恢复；应通过实体按键、App 或其他受控入口提交 `single`/`4D01`。

当前真板只直接观测到 `0x06` 声控状态帧；`0x08`、`0x10`、`0x12` 等长度由 Byte 2 和通用拆包规则覆盖，并已由主机测试验证解析路径，但仍需真板日志确认其实际出现。

### `10 07` 与 `10 FE` 的 ACK 判断

对当前 `LingyangBoardAdapter` 的普通设置命令，ACK token 由“功能码 + 键值”组成。发送 `10 07` 时，期望匹配 `0x1007`；收到 `10 FE` 的 token 是 `0x10FE`，不能作为当前实现中的直接成功 ACK。

正确结论是“`10 07` 尚未被确认”，而不是仅凭 `FE` 判定失败。除非真板资料明确规定 `10 FE` 是设置拒绝回报，否则必须继续等待匹配 ACK 或执行综合状态查询；最终没有匹配 ACK 且超时，才进入 `timeout/failed`。

### `10 FE 08 03` 的字段边界

```text
... 10 FE 08 03 00 ...
         │  │  │
         │  │  └─ Byte 6
         │  └──── Byte 5
         └─────── Byte 4，查询标志
```

协议表没有明确规定 `0x10/0xFE` 回包的 Byte 5/6。只有 `0x3F/0xFE` 综合状态表明确规定 Byte 5/6 为剩余分钟/秒。因此可以说：

- 若该主板实测复用综合状态布局，`08 03` **可能**是 8 分 3 秒；
- 不能把该解释伪装成 V0.35 表格的明示结论；
- 通过 `3F FE` 回包、连续倒计时采样或厂家确认验证后，才可固化映射。

## 当前仓库代码的核对点

检查这些位置，避免只按日志文字推断：

- `xiaozhi-esp32/main/massage/lingyang/lingyang_constants.h`：`kQueryValue = 0xFE`，`kTime = 0x10`。
- `xiaozhi-esp32/main/massage/lingyang/lingyang_frame_decoder.h`：`function_code()` 读取 `bytes[3]`，`value()` 读取 `bytes[4]`，当前长度边界为 `kMinFrameLength=6`、`kMaxFrameLength=128`。
- `xiaozhi-esp32/main/massage/lingyang/lingyang_board_adapter.cc`：RX 日志直接打印功能码、Byte 4 值和实际长度；普通命令 ACK token 由功能码和值构造，`0x4D/0xFE` 查询回帧只在此适配层生成。
- `BuildStatusQueryPlan()` 当前发送 `0x3F/0xFE` 综合状态查询和 `0x02/0xFE` 电源查询，不要无依据地声称当前刷新链路发送了 `0x10/0xFE`。
- `xiaozhi-esp32/main/massage/lingyang/lingyang_status_decoder.cc`：普通功能码继续要求 20 字节；`0x4D` 使用最小 6 字节并按 Byte 2 允许可变长度，只读取 Byte 4。功能码 `0x10` 仍使用 Byte 4 计算 `remaining_sec = value * 60`，不会读取 Byte 5/6；若真实主板发送 `10 FE 08 03`，必须把它标为当前解析逻辑与真板回包布局不一致，不能声称固件已正确解析成 8 分 3 秒。
- `xiaozhi-esp32/tests/lingyang_protocol_test.cc`：覆盖 `0x4D` 的 `0x06/08/0A/0C/0E/10/12/14` 可变长度、`0/1/2` 值、长度一致性、校验和和状态映射；这些兼容形状测试不等于真板已发送。

## 输出格式

回答单条报文时，按以下顺序输出：

1. **结论**：一句话说明确定语义和确定性等级。
2. **字节表**：至少列出帧头、长度、功能码、键值/查询标志、关键数据、校验和。
3. **校验结果**：给出实际长度和低 8 位校验结果。
4. **协议依据**：写明 XLS 工作表/行或源码/测试路径；区分明示与推断。
5. **执行状态**：使用 `accepted`、`sent`、`acknowledged`、`completed`、`failed`、`timeout` 或“未确认”，不要把“收到合法帧”写成“设备已执行”。
6. **待确认项**：列出所需的相邻 TX、后续 `3F FE` 回包或真板实验。

## 不要做的事

- 不要把 `0xFE` 当成失败码或成功码。
- 不要把校验和正确当成业务执行成功。
- 不要把 `10 FE` 当成 `10 07` 的匹配 ACK。
- 不要因为 `0x4D` 入站帧小于 20 字节就判为无效，也不要把它误写死为只能是 6 字节。
- 不要把 `0x4D` 额外字节当成已有业务字段；除非有直接报文、协议依据和适配层黄金测试，否则保留原始帧并标记未知。
- 不要在 `0x10` 回包中未经证据把 `08 03` 定义为分钟/秒。
- 不要把历史 XLS、旧 AI-Massage 代码或主机单元测试写成真实硬件已经确认。
- 不要让服务端、MassageAgent 或通用 UART 生成或解析岭阳裸帧；需要改代码时只在岭阳适配层扩展并补测试。
